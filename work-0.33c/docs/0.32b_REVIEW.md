**Reading of finding 3, for owner review:** the documented contract (design §4) says one overrun makes a service
DEGRADED and three in a row make it FAILED. The probe is a step, so 0.32b applies that rule to it unchanged. A
service whose probe was slow is RUNNING but DEGRADED, and it fails after two more slow steps. The alternative,
refusing readiness on a slow probe, would be stricter than the contract for loop steps. It was not taken, and it is
one change in `try_start` if wanted.

## 4. Limits and exceptions

1. **Finding 2 has hosted evidence only.** The QEMU TSC never runs backwards, so an unmeasured step cannot be
   produced on the VM.
2. **Production readiness is now strict about time.** The counter's 1-unit probe must be measured in budget, or C12
   fails. On a heavily loaded host, a genuine >1 ms probe would be reported honestly (OVERRUN, DEGRADED), and C12
   would then fail that run. It did not happen in 16 counted boots.
3. **The design's limits remain:**
   - the cooperative limit (a step that never returns hangs the kernel);
   - the stall misattributed as a TSC jump (Y013);
   - a perfectly consistent lying service cannot be caught;
   - `reason=NONE` on failure rows (D-ABR-019 Q3-B);
   - static checks are text and byte scans.
4. **Post-close tools** (written after `campaign close`, not code under test): `evidence_index_032b.py`,
   `make_audit_032b.py`, `check_checklist_032b.py`. They were drafted in the session scratchpad during the campaign
   and copied in after close, so the campaign's source manifest never saw them.
