# ABRAHAM 0.33c: the two audit clarifications (D-ABR-026 Phase 3)

2026-11-10. Directive `MOSKO_ABRAHAM_033C_FINAL_AUDIT_DIRECTIVE_2026-11-10.md`, Phase 3.

**Neither clarification needs a kernel change.** The kernel's clock guard behaves safely in every case examined:
DEGRADED is latched, observations become UNKNOWN / OBSERVATION_STALE, and nothing is SATISFIED on stale data. Both
findings concern the host launcher's reporting and the verifier's coverage. They are corrected in launcher **0.33.2**
(tree `vmlauncher-0.33.2`), in a separately recorded corrective scope. Launcher 0.33.1 and its records stay as they
are.

## A. Kernel-reported clock gaps: a discontinuity, not a cause

**The question.** A `TSC_FORWARD_JUMP` with a matching `HEARTBEAT_GAP` shows that the kernel observed a
discontinuity. Does it establish the cause?

**Finding: no. Launcher 0.33.1 overstated it.**
- The DIAGNOSTIC build `diag-tsc-jump` injects a one-hour TSC jump *inside the guest*. Runs O003 (WHPX) and O004 (TCG)
  of TR-0042 each lasted about 15 s, with no host pause at all.
- Their kernel reports are the same shape as after a real laptop standby (TR-0045):
  `TSC_FORWARD_JUMP`, then `state=DEGRADED`, then `HEARTBEAT_GAP|from_s=3|to_s=3603|skipped=3599`.
- Launcher 0.33.1 labels both "host pause, reported by the kernel". **That is a false causal claim.**
- A guest-side stall longer than 5 s (a kernel defect that blocks the heartbeat loop) would produce the same report.
- A host-side stop of the QEMU process alone, as in the tests' freeze, also produces it. In that case the host did
  cause the gap, but nothing on the host shows it.

**What host evidence can establish.** When Windows suspends programs (standby, sleep), the launcher process stops too,
and its own loop sees the jump in time on resuming. Evidence about the kernel's gap therefore comes in three kinds:

| Evidence | What it establishes |
|---|---|
| The kernel's report alone | a discontinuity of N s in the guest's view. Cause: **not established** |
| The kernel's report, and the launcher itself stopped for a comparable time just before it arrived | a **host suspension** (the host stopped programs), so the gap's cause is on the host side |
| The kernel's report while the launcher kept running | the cause is **not established**: QEMU alone was stopped, or the guest stalled. The launcher cannot tell these apart |

For the real standby of TR-0045, the Windows power log (Kernel-Power 506/507) is the host evidence: it is recorded
there. The 0.33 launcher that ran that test did not yet measure its own stops.

**Correction in 0.33.2:**
- The words "host pause" are gone. The panel, the record and the result block say "clock gap reported by the kernel",
  and give the cause as one of:
  - "host suspension (the launcher was stopped N s too)";
  - "cause not established (the launcher kept running)".
- The launcher records each stop of its own loop longer than 2 s, on both the monotonic clock and wall time. A gap
  counts as a host suspension only if the launcher stopped for at least half its length, ending within the 30 s before
  the kernel's report arrived.
- A run with any clock anomaly the host evidence does not explain ends with a new result,
  `CLOCK_ANOMALY_CAUSE_NOT_ESTABLISHED` (exit 11), not OK. This includes a backward TSC.
- The boot verdict stays PASS where the kernel booted, and the stale-data behaviour is judged as designed.
- Nothing about the kernel's DEGRADED / UNKNOWN behaviour changes.

**F-VML-03, found while examining A.** In O003/O004 the first status round after the jump still says `clock=OK`, because
the guard reports the jump 36 ms later. This is the detection window TR-0042 §5 item 3 already documents.
- Launcher 0.33.1 applied C12's round spacing to that round, and so called the services wrong ("3,602,925 ms after the
  previous round").
- The official judges do not apply C12 once the clock degrades.
- In 0.33.2, C12's progress and spacing findings count only on a run whose clock never degraded. Otherwise they are
  recorded as "not counted after degradation".

**Classification:**
- **A** is a launcher reporting correction (an operator-facing causal overstatement). It is not a release blocker for
  the kernel. For the launcher it is a truthfulness defect, corrected in 0.33.2.
- **F-VML-03** is a launcher defect (a services verdict that disagrees with the official degraded-clock judge),
  corrected in 0.33.2.

**Limitation that stays (documented, not removable):**
- From inside the guest, a host stop of QEMU and a guest stall are indistinguishable.
- From the host, the launcher sees only its own stops.
- A host stop of QEMU alone, by a debugger or by a test tool such as `pause_qemu.py`, is reported "cause not
  established". That is true: the launcher has no evidence of it.

## B. The launchpad build on a degraded clock: a composite judge

**The question.** TR-0046 P004 is NOT VERIFIED because no official judge covers the DIAGNOSTIC launchpad on a
DEGRADED clock. Can a judge be added without changing the application contracts?

**Why neither official mode fits:**
- `launch_probe launchpad` requires `counter_available_and_increasing_every_round`, which a DEGRADED clock forbids by
  design.
- `launch_probe degraded-clock` requires `no_launch_line`, which the launchpad build contradicts by design.
- Everything else in both modes applies unchanged.

**Answer: yes.** `vmlauncher-0.33.2/tools/judge_launchpad_degraded.py` is a COMPOSITE judge. It imports the official
rule sets read-only and only selects and combines them:
- every check of the launchpad mode except the counter-AVAILABLE rule. These include the 0.32b service checks, the
  17-row design script, transitions, fact rules, facts against the round, discovery, the routed request, the summary,
  the refused RUNNING transition, no execution claim and registered codes;
- the two degraded-clock rules: `counterview` SATISFIED before the anomaly, and UNSATISFIED on stale data after it;
- one applicability check: the kernel itself reported `state=DEGRADED`.

It adds no rule of its own and changes no application contract. Its verdict is labelled COMPOSITE, never official.

**Tested** (self-test, 9 cases, all correct in development):
- **Passes:** TR-0046's P004 log.
- **Rejected for the intended reason:**
  - a stale counter claimed AVAILABLE;
  - `counterview` SATISFIED on stale data;
  - an execution claim;
  - a missing transition;
  - a miscounted summary;
  - a missing DEGRADED report.
- **Non-vacuity controls:** it fails on a normal launchpad run, and on a production run with a degraded clock.

**Classification: future improvement, delivered.** It is not a release blocker: P004's live verdicts were never
claimed as an official judgment. The launcher's result block says "Not claimed: the official C0-C13 judgment". The
0.33.2 verifier now judges such runs with the composite judge, and marks them so.
